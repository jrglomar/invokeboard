# ADR-084: Teams — a shared team scope, credentials stay personal (v1.73, Wave 1)

## Status: Accepted (2026-08-04) — implemented in v1.73 (Wave 1 of 3)

## Context

Multi-tenancy today (ADR-055/056/077/078) is strictly PER-USER. Every stored document — leaves, meeting
notes, meeting goals, PRs, retro, impediments, offset, the local `team` roster, the draft capacity plan —
is keyed by `(scope, name)`, and scope resolves to exactly one thing: the signed-in user's own id, or the
id of the user whose credentials they borrow (ADR-056's `sharedFrom`). Two teammates working the same board
who are NOT on shared credentials therefore see two completely disjoint sets of leave requests, retro
notes, and impediments — there is no way for a group of users to collaborate on the same documents while
each keeps using their own Jira/GitHub token.

The existing mechanism that comes closest — `credentialSourceUserId` delegation — was built to solve a
different problem (onboarding a teammate with NO tokens at all) and its side effect (shared storage,
ADR-056 §9.8.1) is a coincidence of implementation, not a feature: delegation forces every borrower onto
the SAME Jira token, which (a) misattributes every write to the token owner in Jira's own history and (b)
requires the whole team to have no credentials of their own. That is unacceptable for a team where everyone
already has, and wants to keep using, their own Jira login — reusing delegation for "sharing" would mean
either giving up personal tokens or giving up shared documents. Users need both at once.

The centralized scope resolution ADR-077 built (`currentScope()` in `storage/index.ts`, fed by
`getRequestStoreUserId()`) makes the fix structural rather than a sweep through 47 tools: whatever
`resolveUser()` decides `storeUserId` is, every one of the 10 shared stores picks it up for free.

## Decision

**A team is a THIRD scope input, independent of credential delegation.** `StoredUser` gains `teamId?:
string | null`. `resolveUser()` (userConfig.ts) computes:

```
const team = user.teamId ? findTeamById(user.teamId) : null;   // defensive: deleted team ⇒ no team
const storeUserId = team ? teamScope(team.id) : (sharedFrom ?? userId);
```

Team wins for **scope** (which documents you read/write); `sharedFrom` — ADR-056 delegation — is completely
untouched and keeps deciding **credentials** (which Jira/GitHub/AI token you act with). A user can be in a
team AND on borrowed credentials at the same time; the two questions no longer collide.

**Teams live inside the existing `users` doc**, not a new store — `teams: Record<string, Team>` alongside
the proven `configTemplates` pattern from ADR-057 (§9.9). This was the deliberate, low-risk choice over a
dedicated `teams` store:

- No new entry in `storage/registry.ts`'s `SHARED_STORE_NAMES`/`OVERRIDE_BY_NAME`, no new `*_FILE` env var,
  no new sqlite-driver doc name to add to the auto-import scan.
- A team and its members' `teamId` are edited through the SAME `read()`/`write()` round-trip as the rest of
  the account data, so they can never drift out of atomic consistency (no risk of a team existing in one
  store while a stale reference to it sits in another).
- `ConfigTemplate` already proved this exact shape (a named, admin-managed record embedded in the users
  doc) works cleanly for CRUD, listing, and case-insensitive name lookup — `Team` mirrors it structurally.

**The `team-` prefix, not `team:<id>` or a bare id.** `teamScope(id)` returns `` `team-${id}` ``. Two
reasons this exact string:

1. **Uniqueness against real user ids.** Scope collides with a real user's per-user directory if a team id
   and a user id could ever be equal. `crypto.randomUUID()` values never begin with the literal `team-`
   (or any word prefix), so prefixing makes the two id spaces provably disjoint without a lookup.
2. **Filesystem safety.** The json driver turns a scope string directly into a directory name
   (`<userStoresDir>/<scope>/<name>.json`, ADR-077). A colon (`team:<id>`) is a reserved character in a
   Windows path component — `team:abc` would either be rejected by the OS or (worse) silently misinterpreted
   as an NTFS alternate-data-stream reference (`file:stream`). A hyphen has no such meaning on any of the
   platforms this repo targets (Windows dev, Linux Docker). This is not theoretical for InvokeBoard: the
   dev environment IS Windows (see CLAUDE.md/MEMORY), so a colon would have broken team storage on day one.

**Team-level config is a real merge layer, not cosmetic.** Inserted between the admin global defaults and
delegation/per-user overrides:

```
.env base ← admin global ← team config ← source's overrides ← the user's own overrides ← creds
```

Without this layer, two team members could point at different `JIRA_DEV_BOARD_ID`s (their own per-user
override, or simply different global defaults if the admin never unified them) while sharing the SAME
leaves/retro/meeting-notes documents — a leave request logged against "the team's" storage while each
viewer's UI shows a different sprint's dates entirely. A team-level config gives an admin one place to pin
the board ids/env every member of a team should see, closing that gap structurally rather than by
convention.

**The `journal` carve-out is preserved unchanged.** A journal is explicitly per-real-user (ADR-056 already
established this for delegation — a borrower's journal never merges with the source's); team scope follows
the identical rule for the identical reason: personal notes are personal, even inside a team.
`TEAM_SCOPED_STORE_NAMES` is therefore defined as `SHARED_STORE_NAMES` minus `"users"` — deliberately NOT
adding a parallel minus-`"journal"` clause, because `journal` was never in `SHARED_STORE_NAMES` to begin
with (ADR-077 §comment: "journal is deliberately absent").

**Wave 1 scope.** This ADR and this phase implement the DATA MODEL and scope-resolution mechanics only:
`Team`/`teamId` types, `userStore.ts` CRUD, `resolveUser()`'s 4-line change, `TEAM_SCOPED_STORE_NAMES`, and
`adoptScopeDocs()` (a one-time, non-destructive seeding helper so a new team doesn't start empty when its
first member already has leaves/retro/etc. under their own id). No route, no tool, and no UI changes — the
admin REST routes in CONTRACTS §9.10.6 are documented now so the contract is settled before Wave 2 builds
against it, per THE RULE (contract before surface), but they return nothing yet; Wave 2 wires the routes,
Wave 3 wires the admin UI.

## Consequences

- A team's members share leaves/meeting notes/meeting goals/PRs/retro/impediments/offset/the local team
  roster/draft plan with zero changes to any of the 47 tools — scope resolution was already centralized by
  ADR-077, so this phase only had to teach `resolveUser()` a new scope source.
- Team scope and credential delegation are now fully orthogonal: a team can be built from members who each
  keep their own Jira token (the common real-world case) — delegation remains available separately for the
  "no tokens at all" onboarding case it was built for.
- A `teamId` pointing at a deleted team fails safe (falls back to `sharedFrom ?? userId`), never a crash —
  deleting a team can never orphan a user's request into an unresolvable scope.
- The `users` doc's shape grows by one field (`teams`) and one optional field on `StoredUser`
  (`teamId`); both are read with the same tolerant-default convention every other field in that file
  already uses, so pre-v1.73 `users.json` documents (real or in old test fixtures) still load correctly —
  `teams` defaults to `{}`.
- `adoptScopeDocs` is intentionally one-directional and non-destructive — it is a seeding convenience, not
  a sync mechanism; once a team's document exists, it is never silently overwritten by another member's
  older copy.
- Tests: mcp-jira 685 → **704** (+19: team CRUD, `teamScope`, `listUsersByTeam`, `teamId: null` clear,
  legacy-doc tolerance, `resolveUser` team-scoping + deleted-team fallback + config merge precedence,
  same-team/cross-team `storeUserId` isolation, journal carve-out under a team, `adoptScopeDocs`
  copy/skip/idempotency). No route, tool, or react-app changes in this wave.

## Alternatives considered

- **Reuse `credentialSourceUserId` for sharing** (point every team member's credential source at one
  another, or at a shared "team account"). Rejected in Context above — forces one shared Jira token,
  misattributing every write, and is incompatible with members who already have their own credentials.
- **A dedicated `teams` store** (new registry entry, new `*_FILE` override, own read/write cycle).
  Rejected — `configTemplates` already proved the embedded-in-`users` pattern works, and a separate store
  reintroduces the exact cross-store drift risk (team exists, membership reference stale, or vice versa)
  that keeping them in one doc avoids for free.
- **`team:<id>` or a bare UUID as the scope string.** Rejected — a colon is unsafe/ambiguous in a Windows
  path component (this repo's dev platform), and a bare UUID risks an eventual collision with a real user
  id with no cheap way to rule it out; the `team-` prefix is both filesystem-safe and provably disjoint.
- **No team-level config layer** (let team members simply live with whatever board id their own `.env`/
  per-user override gives them). Rejected — silently produces the "shared leaves, different sprint dates"
  inconsistency described above; a team-level layer is one extra line in the merge and closes it.
- **Making `journal` team-shared too** ("the team's notes"). Rejected — journal has always been the one
  deliberately personal store (ADR-056 carve-out); nothing about team membership changes that intent, and
  changing it now would silently expose one member's private notes to the rest of the team.
- **Building the admin routes/UI in this same wave.** Rejected — the task was scoped to the storage
  mechanics as Wave 1 specifically so the contract could be reviewed and settled (THE RULE) before Wave 2
  spends effort wiring routes against it, and Wave 3 spends effort on UI against those routes.
