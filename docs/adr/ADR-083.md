# ADR-083: Link existing Dev tickets to a PO story, and roll Dev tickets up into a new PO story (v1.72)

## Status: Accepted (2026-07-27) — implemented in v1.72

## Context

Since ADR-003 a PO↔Dev link has been a generic Jira issue link, and since ADR-022 the Linking page
has created those links in bulk. But every link in the product is still born in exactly one place:
`create_dev_ticket` (§4.2). `createIssueLink()` has a single caller, and there is no `link_issues`
tool, no unlink tool, and no UI anywhere that lets a user pick an already-existing Dev ticket.

That leaves three real gaps:

1. **A Dev ticket that already exists can never be attached to its PO story.** Tickets raised
   directly on the Dev board, or carried over from a previous sprint, are permanently unlinkable —
   the only way to link them is to abandon them and re-create the work through the Linking page.
2. **The inverse direction is unsupported.** Sometimes the Dev tasks land first (a spike, a bug
   cluster, work a developer started before grooming) and the PO story that covers them has to be
   written afterwards. The product only models PO → Dev.
3. **A wrong link is permanent in-app.** `get_linked_issues` never returned the Jira link id, so
   nothing in the UI could target a `DELETE /rest/api/3/issueLink/{id}`. Mis-links had to be fixed
   in Jira directly — and the more linking the product does, the more mis-links it can make.

None of this is a data-model problem. `get_linked_issues` has always returned an **array** per key,
ADR-046 already ships 1–2 Dev tasks per PO story by point breakdown, and the user guide already says
"the PO story 'depends on' its Dev task(s)". Many-Dev→1-PO is the shipped, intended shape; what was
missing is a write path. (The "one or none" phrasing surviving in ADR-022 and CONTRACTS §4.17 was
only ever a *selection heuristic* — an already-linked PO is deselected by default but still
selectable — never a constraint. v1.72 corrects that wording.)

## Decision

Contract updated first (`CONTRACTS.md` §4.9, §4.17, new §4.31/§4.32, §6), per THE RULE.

**1. Two domain tools, one pair per call, the client loops.** New `link_dev_to_po({ poKey, devKey })`
and `unlink_dev_from_po({ linkId, poKey?, devKey? })`.

Deliberately **not** a generic `link_issues({ inwardKey, outwardKey })`. The direction invariant —
PO on `inwardIssue`, Dev on `outwardIssue`, so the PO reads "depends on" its Dev task — is the most
error-prone thing in this subsystem: it is counter-intuitive (the inward issue displays the type's
*outward* description), it shipped backwards once and was swapped in v1.42 (ADR-046/ADR-052), and
`createDevTicket.ts` carries a four-line comment explaining it. A generic tool re-exports that trap
to every caller, including Copilot over stdio, which has no UI to get it right. Domain-shaped
parameter names make the invariant unstateable-wrongly.

Deliberately **not** a server-side bulk `link_dev_to_po({ poKey, devKeys[] })` either. §6 already
sets the precedent ("No new bulk MCP tool — the client loops `create_dev_ticket`"), the client
already owns per-item ✓/✗ and "Retry failed", and a bulk tool would need to invent a partial-success
vocabulary the UI already has.

**2. Linking becomes a 3-mode page rather than three tabs.** `pages/Linking.tsx` drops to a shell
owning the shared sprint context, a mode toggle, and a render switch; each flow is its own component
under `components/linking/`. The two sprint selects change *meaning* per mode (source vs target) but
keep their accessible names, so a11y queries stay stable. One page, one mental model, no duplicated
sprint-picker code — and the 707-line file stops growing.

**3. `get_linked_issues` carries the link identity.** `LinkedIssueRef` gains `linkId`,
`linkTypeName`, and `direction`, all read from the payload the tool **already fetches** — no extra
Jira call. `direction` is not redundant with the key prefix: Jira returns only the *other* side of a
link, so reading a PO yields `outwardIssue: DEV-x` while reading a Dev ticket yields
`inwardIssue: PO-y`. Mode 2 reads from the Dev side, so without `direction` it cannot distinguish a
canonical link from a pre-v1.42 reversed one. The fields are **required** server-side and
**optional** in the react-app type — the server always sends them, and making them required would
force edits to fixture literals in three existing test files for zero behavioural gain.

**4. Idempotency is ours, not Jira's.** Jira's REST API has historically permitted duplicate links
between the same pair with the same type even though the web UI blocks them, and `POST
/rest/api/3/issueLink` answers 201 with an **empty body**, so the response cannot reveal it.
`link_dev_to_po` therefore pre-checks `getLinkedIssues(poKey)` and returns `alreadyLinked` without
posting. Two deliberate refinements: the match **ignores direction** (a reversed legacy link is
still a link; stacking the canonical one on top would leave two rows asserting opposite
dependencies — flagged `reversed: true` instead), and a *failed* pre-check sets `precheckWarning`
and proceeds, because a broken read must never block a legitimate write. The empty 201 body also
means `linkId` is null on the create path; the client refetches `get_linked_issues` once after its
bulk loop rather than spending N read-backs.

Unlink inverts the same caution: when both keys are supplied it verifies the link id actually
connects that pair and throws otherwise (an `UpstreamError` marked 409, which the bridge surfaces
as `502 UPSTREAM` like every other upstream failure — the message is what the user sees), so a
stale UI can never delete an unrelated link. A
404 from the DELETE is treated as success — Jira returns 404 both for "already gone" and "you can't
see it", and the two are indistinguishable.

**5. AI drafts the rolled-up PO story; arithmetic stays deterministic.** New bridge-only
`POST /api/ai/draft-po-story` (§4.9) — the inverse of `plan-dev-tickets` — writes one PO story
covering N Dev tasks, with a `lib/poRollup.ts` deterministic fallback so the flow never blocks when
AI is off. It deliberately does **not** return story points: the new story's points are the *sum* of
the selected Dev tickets' points, exact arithmetic the client computes and seeds into an editable
field. Asking a model for a number it cannot compute better invites a wrong value the user must
catch. (Contrast §4.9 `draft-tickets`, which does estimate — there is no source figure to sum.)

**6. Both new tools join `JIRA_WRITE_TOOLS`, neither joins the AI allowlists.** They mutate Jira, so
a shared-credential read-only user must get `403 READ_ONLY_USER` (ADR-056). They are *not* added to
the Ask assistant's write-allowlist: the assistant has no linking workflow, and every proposal
surface needs its own confirmation copy (ADR-030). The two new modes also read `readOnly` and
disable their submit controls, so a borrower sees one explanation instead of N × 403 log rows.

## Consequences

- Links can finally be created between existing issues, in both directions, and removed — closing
  the three gaps above without touching the link semantics ADR-003/046/052 established.
- The Linking page is now four focused files instead of one 707-line file, and the extracted
  primitives (`useBulkRun`, `BulkStatusLog`, `SprintSelect`, `flattenIssues`) remove duplication
  that had spread across up to five call sites.
- **Mode 3 has one genuinely dangerous failure mode**, handled by design: if the PO story is created
  and some links then fail, "Retry failed" must re-link only. The created key is held in state and
  `useBulkRun.retryFailed` re-runs only `error` rows, so retry can never create a second PO story;
  a failed create aborts before any link, leaving no orphan. Two tests pin this.
- Duplicate-link prevention now depends on our pre-check rather than on Jira. A known asymmetry
  follows: `JIRA_LINK_TYPE` is per-user overridable (ADR-055), so dedupe — which filters on key **+
  the current user's configured type** — cannot see a link created under a different type. The UI
  compensates by badging "already linked" for links of *any* type; only the skip-the-POST decision
  is type-scoped. Documented in §4.31 so it doesn't read as a bug.
- Pre-existing limitation left alone and recorded: `get_active_sprint` rejects a closed sprint id,
  while mode 1's PO picker still offers closed sprints. The new source pickers offer active+future
  only, so they don't reproduce it; repairing mode 1 is out of scope for this phase.
- Tests: mcp-jira 661 → **685** (+24: link direction invariant, type-scoped dedupe, reversed-link
  flagging, pre-check resilience, self-link/malformed rejection, the four unlink-guard paths,
  `linkId`/`linkTypeName`/`direction` pass-through, bridge round-trip, the `READ_ONLY_USER` 403
  regression guard, and `draft-po-story` 503/400/happy-path/not-a-tool); react-app 1108 → **1142**
  (+34: `poRollup` 7, `useBulkRun` 4, `SprintSelect` 3, `DevTicketPicker` 4, `LinkExistingMode` 7,
  `NewPoFromDevMode` 8, `aiDraftPoStory` 1 — the two load-bearing ones being "PO-create failure ⇒
  zero link calls" and "retry re-links only, `create_po_ticket` called exactly once");
  mcp-github 57 unchanged — total 1,826 → **1,884**; smoke 61 → **62** (`draft-po-story` 503
  parity; expected jira tools 45 → 47). react-app version pill 1.71.0 → **1.72.0**.

## Alternatives considered

- **A generic `link_issues({ inwardKey, outwardKey })`.** Rejected — re-exports the direction trap
  to every caller including Copilot; the invariant has already been shipped backwards once.
- **A server-side bulk loop over `devKeys[]`.** Rejected — contradicts the §6 client-loops
  precedent, duplicates partial-success reporting the UI already has, and puts N Jira round-trips
  inside one request.
- **Unlink by `(poKey, devKey)` without a link id.** Rejected — ambiguous when a pair carries
  several links of different types, and it would delete the wrong one silently.
- **Reading the new link back after each create** to obtain its id. Rejected — N extra GETs for
  data one batched refetch provides, which the UI needs anyway to refresh badges.
- **Trusting Jira to reject duplicate links.** Rejected — the REST API has historically allowed
  them where the web UI does not, and the empty 201 body makes it undetectable.
- **Asking the model for the rolled-up story points.** Rejected — the sum is exact arithmetic; a
  model estimate would be a wrong number the user has to notice.
- **Two new sidebar tabs (or one new tab hosting both flows).** Rejected — three linking-ish tabs
  in the sidebar, plus duplicated sprint-picker state and code, for flows that share their entire
  context.
- **Modal confirmation for unlink.** Rejected — `ConfirmActionDialog` is bound to `ProposedAction`
  + `callTool` and there is no `ui/alert-dialog`; an inline two-click confirm matches the row-level
  weight of the action.
