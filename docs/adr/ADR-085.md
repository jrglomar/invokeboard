# ADR-085: MySQL storage driver (write-behind cache) + portable data export + production compose (v1.74)

## Status: Accepted (2026-10-07) — implemented in v1.74

## Context

Since v1.65 (ADR-077) the live single-host Docker stack stores everything — leaves, team, users and their
sealed tokens, retro, journals, teams' shared docs — in one sqlite table `docs(scope, name, data,
updated_at)` on the `invokeboard-data` volume. Two needs drive this change:

1. **Get the data out.** There was no off-box copy of the volume and no format for moving it anywhere.
2. **Move to a server on MySQL**, with a deploy setup fit for that server (no host-exposed bridge
   ports, backups, a runbook).

The hard constraint is ADR-077's **synchronous** storage port (`readDoc`/`writeDoc`). Twelve store
modules, `adopt.ts`, and every tool/route above them are sync because better-sqlite3 is sync. Every MySQL
client for Node is async. Making the port async would ripple through ~50 tools and their tests for no
functional gain.

## Decision

1. **`STORAGE_DRIVER=mysql`: a write-behind cache over the same one-table shape.** `init()` (awaited
   once at startup through `initStorage()`) creates `docs` and preloads every row into memory. Reads are
   synchronous map lookups plus `JSON.parse`, so each caller gets a fresh object, like sqlite. Writes
   update the cache synchronously and are persisted by a single serialized pump. Repeated writes to a
   key coalesce to the latest value. A failed upsert is re-queued and retried with capped exponential
   backoff, and it is logged, never thrown into the request. `flushStorage()` drains the queue, bounded
   at 8s. Both entries call it on SIGTERM/SIGINT, and the prod compose file gives `jira` a 15s stop grace.
   The port gains three **optional** members (`init`, `flush`, `countDocs`); json and sqlite are unchanged.
2. **`data` is `LONGTEXT CHECK (JSON_VALID(data))`, not a native `JSON` column.** MySQL normalizes JSON
   columns and re-sorts object keys, while stores may rely on insertion order (sprint-keyed maps). A text
   column round-trips byte-for-byte like sqlite's TEXT, and `JSON_EXTRACT` and friends still work on it.
   The keys use `utf8mb4_bin`, so they stay case-sensitive like sqlite.
3. **A driver-neutral doc bundle** (`storage/bundle.ts`, format `invokeboard-docs/1`) is the hand-off
   artifact. `storage-export.ts` writes it from sqlite (plus a WAL-safe `backup()` copy) or from json.
   `scripts/export-data.mjs` runs that inside the live container (copying the script in, so it works on
   an image built before v1.74), copies the result to `./backups/<ts>/` along with a raw volume tar, and
   checks the doc count. `storage-import.ts` loads a bundle into the configured driver. It refuses a
   non-empty target without `--force`, then verifies every doc from a **fresh** driver, so mysql re-reads
   the database rather than its own cache.
4. **`docker-compose.prod.yml`** is separate from the local `docker-compose.yml`, which stays on sqlite.
   It runs `mysql:8.4` on a named volume with a healthcheck and no host port. `jira` gates on a healthy
   mysql. Neither bridge publishes a host port, `web` listens on loopback only, `cloudflared` is kept, and
   every service has log rotation. `.env.prod.example` and `backup-mysql.sh`/`restore-mysql.sh` ship with
   it, along with DEPLOYMENT.md §9.

## Consequences

- **The one-replica rule becomes load-bearing.** A second `jira` replica would serve its own stale cache.
  This was already mandated (DEPLOYMENT.md §5.8) and stays mandated.
- **Durability window:** a hard kill (SIGKILL, OOM, power loss) can drop writes still queued, typically
  milliseconds old. A normal `docker compose stop`/`down`/redeploy flushes. Writes from outside the
  bridge (manual SQL, restore) are invisible until `jira` restarts; `restore-mysql.sh` stops and starts
  it for that reason.
- **Memory:** the whole store lives in RAM. At today's size (19 docs) that is trivial. It would matter
  only at orders of magnitude more per-user data, at which point a real async port (or per-store tables)
  is the next step.
- No store, tool, route, or UI changed. Tests stay keyless and offline: the mysql driver runs against an
  in-memory fake pool, `mysql2/promise` is `vi.mock`ed, and the json/sqlite/mysql drivers share one
  contract suite.

## Alternatives rejected

- **Async port.** Correct but a large ripple for no user-visible gain at this scale. Revisit if multiple
  replicas or large data are ever needed.
- **Sync MySQL via a worker thread + `Atomics.wait`.** It blocks the event loop on every network round
  trip and is fragile.
- **Normalized per-store tables.** Rewrites every store. The doc table keeps the 1:1 port with sqlite,
  and the user chose the doc shape.
